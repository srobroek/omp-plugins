# Delivery and tooling

Asset sets are applied in this order. Each set contributes static files or bounded fragments;
no set is an unlisted orchestration engine.

| Order | Set | Contributes |
|---|---|---|
| 1 | `skill://project-setup/assets/base/` | `.editorconfig`, `.gitattributes`, `README.md`, and the gitignore fold script |
| 2 | `skill://project-setup/assets/governance/` | `LICENSE.source`, ownership, security, contribution, conduct, and governance templates |
| 3 | `skill://project-setup/assets/hooks/` | `.pre-commit.d/` fragments, hook binaries, and the merge script |
| 4 | `skill://project-setup/assets/ci/` | GitHub quality, security, gate, changes, language workflows, caller generator, and `ci-sync` recipe |
| 5 | `skill://project-setup/assets/forge/` | Forge-specific issue or merge-request templates and the GitLab root pipeline |
| 6 | `skill://project-setup/assets/release/` | Renovate and release-please configuration, plus the supported GitHub release workflow |
| 7 | `skill://project-setup/assets/steering/` | `docs/agents/`, `AGENTS.md`, the `CLAUDE.md` link, and the steering generator |
| 8 | `skill://project-setup/assets/just/` | the root `justfile`, which imports each `.just.d/` fragment |
| 9 | `skill://project-setup/assets/worktrunk/` | `.config/wt.toml` and `.worktreeinclude` |

Just remains late because its import block is generated from `.just.d/`. The gitignore fold
runs after all language fragments exist. Governance and release files are copied only when
the plan names them and resolves their tokens; they do not imply a generator or registration
service.

## Task surface

Asked: nothing. Recipes exist only where a copied `.just.d/` fragment defines them. A root
`justfile` does not promise a member-management command.

Fixed: `just` at the root of every repository, pinned to `1.57.0` in
`.mise/conf.d/just.toml`. `[group(...)]` needs just 1.27 or later and `import?` needs 1.21.

The import block uses `import?`, the optional form. A hand-removed fragment therefore affects
only its own recipes instead of making every root recipe a parse error.

`set shell := ["bash", "-uc"]` is deliberate: macOS ships bash 3.2, where `mapfile` and
`readarray` do not exist.

For a monorepo, use the accepted member paths and run a member's existing language recipe with
its path. No additional package-orchestration layer is supplied.
For a polyrepo, run each checkout independently and ask permission before reusing a related
repository's choices.

## Hooks

| Question | Default | Notes |
|---|---|---|
| Excluded paths | none | `@@HOOK_EXCLUDE_PATTERNS@@`, regexes joined with `\\|` |
| Maximum staged file size, in kilobytes | `500` | `@@MAX_FILE_KB@@` |
| Allowed commit scopes | none | `@@COMMIT_SCOPES@@`, comma-joined |

Say at apply time that scopes are unrestricted when the user named none. `prek` is the fixed
manager with builtin hygiene hooks, betterleaks, trufflehog, typos, shellcheck, conventional-
pre-commit, actionlint, zizmor, taplo, and lychee. Offer `pre-commit` only when the user asks
for it by name.

`.pre-commit-config.yaml` is generated from `.pre-commit.d/` by `just hooks-merge` and is never
edited directly. `hooks-merge` runs through `uv run --no-project --with pyyaml` because the
merge script imports yaml.
The hooks asset also resolves `@@UV_VERSION@@` to the exact latest-stable `uv` value accepted
during setup, even when the repository has no Python layer; hooks need `uv` for their YAML merge.

## CI composition

Asked: nothing beyond the per-job timeout and default branch, settled in repository and hosting.
`@@JOB_TIMEOUT_MINUTES@@` fills the workflow templates.

For GitHub, `.github/workflows/ci.yml` is generated by `scripts/gen_caller.py`, which reads the
language workflow files and rewrites the whole caller. A language is adopted only when its
workflow and filter entry are present. For GitLab, `.gitlab-ci.yml` includes
`.gitlab/ci/*.yml`; the root pipeline is a static asset and no unstated stage generator exists.

A repository on Gitea, Azure DevOps, or another forge is an explicit unsupported CI gap. Do not
copy GitHub or GitLab files and call them support for that forge.

A GitHub runner has no mise. Each language's own CI files therefore install its tools, reading
the same `*_VERSION` tokens `.mise/conf.d/` reads, so a local recipe and a CI job run one build
of each tool: `setup-ts` pins bun, `setup-python` pins uv, `setup-rust` pins the four cargo
tools, and `wc-lint-go.yml` pins golangci-lint and govulncheck where the action they belong to
installs neither. No GitHub path resolves `latest` or `stable` for a tool whose output decides
whether the gate passes. GitLab jobs install through mise directly and inherit the pins with
nothing further.

The GitHub graph is:

```
changes ─┬─> lint-<lang> ─┐
         └─> test-<lang> ─┤
                          ├──> gate
quality ──────────────────┤
security ─────────────────┘
```

`quality` and `security` read their own fragment directories. `gate` is the only required
status check represented by the static workflow; branch protection itself remains API state.
Jobs that `.ci/members.json` and the reusable workflow tree cannot represent, such as a
container build or an OpenTofu plan, must be taken over explicitly.

## Worktrunk

| Question | Default | Notes |
|---|---|---|
| Worktree setup command | `just setup-worktree` | `@@SETUP_COMMAND@@`, the blocking pre-start step |
| Does the repository run a dev server | no | No deletes the `dev` post-start hook and `[list]` block |
| Dev server command | `just dev` | `@@DEV_COMMAND@@`, asked only when a dev server exists |

`@@FORGE_PLATFORM@@` and `@@FORGE_HOSTNAME@@` come from the repository and hosting topic.
`.worktreeinclude` is copied as-is, with the repository's expensive gitignored directories
added under its closing comment. Both Worktrunk files are required for project provisioning.

## Infrastructure choice

Ask whether infrastructure is described with OpenTofu or a provider CDK. Use the OpenTofu name
consistently. The package supplies no provider-specific CDK implementation and no infrastructure
generator; an unsupported provider or host is recorded as an explicit gap.

## Agent steering

Asked: nothing, unless a `CLAUDE.md` already exists. `@@PROJECT_NAME@@` comes from the
repository and hosting topic. Generated blocks in `docs/agents/` are derived from the files on
disk. `AGENTS.md` is a copy of the generated body, and `CLAUDE.md` is a relative symlink to it.
Required environment variables are named, never valued, in `docs/agents/env/index.md`.

A brownfield `CLAUDE.md` holding text `AGENTS.md` does not carry, or a symlink pointing
somewhere other than `AGENTS.md`, is a conflict rather than a file to replace. Ask
`MERGE|OVERWRITE|SKIP` for that one destination and pass the answer as
`python3 scripts/install_agents_index.py . --claude MERGE`. MERGE appends the existing text to
`AGENTS.md` before linking, OVERWRITE states the loss, and SKIP leaves the file untouched so
the two harnesses read separate files. bd's own copy of `AGENTS.md` needs no answer.

## Governance and release

`assets/governance/` supplies the committed governance documents and a licence selection source.
`assets/forge/` supplies only GitHub and GitLab templates and GitLab's root pipeline.
`assets/release/` supplies Renovate configuration and GitHub release-please inputs. Enabling
Renovate, creating a remote, configuring branch protection, and storing credentials are API or
manual state. A GitLab release process is manual unless the user supplies a separate runner;
no release automation is claimed for it.

## Decision records

Conditional on the beads plugin being installed. When it is, the ADR pre-commit fragment and
renderer are copied from `skill://adr/templates/`; project-setup ships neither. Without the
plugin, `docs/adr` is a plain directory of hand-written records.
