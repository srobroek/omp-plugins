# CAD Design Record

TRIGGER
+ creating or validating a hardware project's `hw/` design record
+ "what goes in the CAD design record", "validate this hardware project"
- modeling a part or assembly → `cad-model`

## Workflow

1. Copy `assets/project-template/hw` into the project. It contains required record-file placeholders and one placeholder BOM row but no part directory; add `hw/parts/<PN>/part.yaml` and `model.py` for each part, using a PN matching `^[A-Z]{2,5}-[0-9]{4}$`. Put BOM rows in `hw/bom.csv`, verification evidence in `hw/verification.csv` and design rationale in `hw/decisions/DR-###.md`. `release.py` writes release packages to `hw/releases/<rev>/`. `hw/.cad/recheck.json` is generated by `cad-recheck` from the staged record; do not copy it from a template.
2. In `assembly.yaml` `drawing.operations`, include `tools` and `consumables` only when the record states them. Never infer tools or process settings.
3. Generate the versioned GitBuilding index with `uv run --script skill://cad-record/scripts/build_guide.py hw --version vN --out docs`. It preserves the `<parts>` tag and uses version STEP paths.
4. Use the DIN SPEC checklist and OKH template references to the generated parts, assembly, and verification sections.
5. Run `uv run --script skill://cad-record/scripts/validate.py <project-dir>`. Read JSON from stdout; exit 0 means no error findings, 1 means at least one error, 2 means usage or infrastructure failed. Warnings stay in the report and do not fail it.
6. Release a frozen version with `release.py` (see Release).

## Layout

`layout.json` owns every path under `hw/`: who writes it, the stage it first appears at, whether it is record source or generated output, and whether it can change. [references/layout.md](references/layout.md) is the generated table. Commands resolve and publish paths through `scripts/layout.py`, described in [references/layout-api.md](references/layout-api.md).

`validate.py` walks every file and folder under `hw/`, tracked, untracked or ignored, without following symlinks. Each path the layout does not accept becomes a finding with `code`, `path`, `canonical_location` and `action`; nothing is moved or deleted. A stray or misplaced path is a warning before `design_freeze` and an error from `design_freeze` on. It stays an error at every stage once `flow.frozen` is set or a release exists. Unsafe names, symlinks that leave `hw/`, and a sealed folder that gained or lost a file are errors at every stage.

MUST Put each file where `references/layout.md` places it. Generated outputs come only from their writer, inside the version or bundle that seals them; never place geometry, export scripts or copies in a folder of your own, such as `hw/print/`.
MUST Keep notes and reference material in `hw/docs/` and procurement copies in `hw/parts/<PN>/sources/`. Scratch work goes in `.cad-work/` beside `hw/`.

For an existing project, `validate.py <project-dir> --migration-plan` prints a read-only plan as JSON. It lists every stray, legacy or damaged path with these fields:

- `classification`: the stray class (`geometry`, `script`, `document`, `data`) or the finding kind, such as `legacy`
- `operation`: `move`, `rebuild`, `remove`, `review` or `keep`
- `destination`: the canonical location, and `destination_exists`
- `rebuild`: the writer that must run to produce the destination
- `confidence`: how sure the layout is of the destination
- `collisions`: other paths with the same destination

Each `confidence` value means one of these:

- `high`: the bytes move unchanged to a determined place, or a leftover goes.
- `medium`: a rebuild produces the destination.
- `low`: you must judge it. The PN is unknown or not a custom-made part, the file is unclassified data, or a link or sealed folder is damaged.

The plan lists built versions without complete manufacturing outputs, and version 1 releases, as `keep`. They stay readable, but nobody can freeze, release or reissue them. `--report PATH` writes the plan to a path under `.cad-work/` instead of stdout. The plan only reads the record and writes only that report.

## Release

`scripts/release.py` issues a release of the frozen version. It copies sealed files and never builds, slices or tessellates.

```bash
uv run --script skill://cad-record/scripts/release.py hw --rev A --version vN --decision DR-###
```

It refuses the release with exit 1 and JSON findings unless all of these hold. On refusal it writes nothing outside `.cad-work/`.

- `product.yaml` `flow.frozen` names `vN` and the sha256 of its `manifest.json`. `DR-###`, the release approval, exists: write it once the RELEASE gate approves, never before. `hw/releases/<rev>/` does not exist: a used revision is never overwritten.
- `validate.py` reports no error. The current record equals the snapshot in `versions/vN/record/`, `product.yaml` `flow` aside, and every `model.py` is the one vN built.
- Every custom-made part has its manufacturing outputs in `versions/vN/manufacturing/<PN>/`, and every manufacturing check passed. FDM needs `part.step`, `part.stl` and `manufacturing.json`. CNC and made-to-drawing parts need `part.step` and `manufacturing.json`. A check failure cannot be waived.
- Each of these has a sealed, passing bundle bound to vN:
  - every part with `drawing` intent
  - the assembly drawing, when `assembly.yaml` declares one
  - every analysis case in `analysis/cases/<id>/`
  - every bundle that a `verification.csv` evidence cell cites
- Every hw/ path that an evidence cell cites exists. Every verification row passes or is waived, and no part has an `X` revision.
- Each `bom.csv` quantity equals the part's occurrence count in the frozen assembly. A built part that only a version's `--attach` entry places counts once.

It stages byte copies in `.cad-work/release-<rev>/` and writes `manifest.json` (release-manifest v2). Next it verifies every copy against the hash of its original. Last it claims `hw/releases/<rev>/` and renames the stage onto it.

| Package path | Copied from |
|---|---|
| `definition/assembly.step`, `definition/record/**` | `versions/vN/assembly.step` and the record snapshot |
| `definition/parts/<PN>/sources/**` | a part's `procurement.specification.artifact` |
| `manufacturing/<PN>/**` | `versions/vN/manufacturing/<PN>/`, custom-made parts only |
| `drawings/<S>/`, `analysis/<S>/`, `checks/<S>/`, `motion/<S>/` | the selected bundle `hw/<kind>/vN/<S>/`, with its manifest |
| `bom.csv`, `verification.csv`, `docs/**` | the current files |

The manifest maps each package file to its `sha256` and `original`. For each custom-made PN it records the `process`, the assembled `quantity` and the files. It lists each selected bundle with its `manifest_sha256`, and a cited render or capture bundle appears there without a copy. A catalog buy has no manufacturing files. Its part.yaml snapshot, specification artifact and vendor sheet define it. A part placed more than once gets one output with its quantity.

## Rules

MUST Use revisions `X1`, `X2`, and so on for prototypes. Use released letters `A` to `Y`, excluding `I`, `O`, `Q`, `S`, `X`, and `Z`.
MUST Set `mass_target` and BOM `mass` in grams; `mass_target` may be null when unknown or not applicable.
MUST Include a `verification` method (`I` inspection, `A` analysis, `D` demonstration, `T` test) and acceptance criteria for every requirement.
MUST Define every joint's `parent` and `child` as references to occurrences included in a subassembly, and include axis, origin in mm, and minimum, nominal, and maximum travel values in its unit (degrees for rotary joints, mm for linear joints). A reference is a PN listed once in subassembly `parts`, or `"@id"` for an explicit occurrence.
MUST Give a joint whose motion follows another joint (gear or belt ratio, cam lift table, slider-crank piston or rod) a `coupling` instead of a `nominal`, with its `profiles` or `mechanisms` entry; keep its `min` and `max`. The coupling contract is cad-motion `scripts/coupling.py`; validate rejects cycles, missing drivers, and derived values outside their limits.
MUST Model one physical part once. A part placed more than once (three identical rings) is one PN with `model_frame: part_local` and one `occurrences` entry per placement, never one PN per placement; its BOM `qty` equals its occurrence count.
MUST Keep BOM columns in this order: `level,PN,rev,qty,title,material,process,make_buy,supplier,mass`, optionally followed by all of `unit,designation,manufacturer,manufacturer_part_number,supplier_part_number,specification_ref,specification_rev`. `level` starts at 0 for a numbered top assembly or 1 for an unnumbered top assembly, then increases by one per child depth; numbered assemblies with BOM children do not need a `part.yaml`. `qty` is instances per parent and `unit` is `pcs`. `mass` copies `mass_target`, and the procurement columns copy part.yaml `procurement`.

### Rigor levels

| Level | Adds |
|---|---|
| `maker` | Clear part identification, assembly interfaces, essential requirements, and basic fit/build notes. |
| `pro` (default) | Traceable requirement sources and verification criteria, controlled revisions, explicit tolerances and fits, complete EBOM, and documented analysis/review evidence. |
| `regulated` | `pro` plus controlled approvals, risk traceability, objective verification evidence, configuration and release records, and change-impact traceability required by the project's governing quality system. |

`regime: iso` applies ISO GPS conventions; `regime: asme` applies ASME dimensioning and tolerancing conventions. State the applicable regime on each product; do not mix symbol or tolerance interpretation between regimes.

## Record files

- `product.yaml`: product identity, rigor, units, drawing regime, general tolerance, and workflow state.
  - `flow.frozen`: the frozen configuration the `design_freeze` gate approved: `version`, the sha256 of its `manifest.json` (`manifest_sha256`), and the approving `decision`. `validate.py` checks the hash against `hw/versions/<version>/manifest.json`.
  - `flow.change`: an open approved change against the frozen version: `decision`, `baseline_version` (the frozen version) and `affected_parts`.
  - Optional `drawing`: the production drawing policy with `definition: model_and_drawing`, an explicit `projection` (`first_angle` or `third_angle`), `standards`, `default_sheet` (`sizes`, `orientation`, `scale`), named `tolerance_policies`, and `general_tolerance_policy`.
  - A tolerance policy is `kind: standard` (ISO 2768-1:1989 with a class) or `kind: limits` (`linear_mm` with its source `reference`). Each names the processes it `applies_to`.
  - `general_tolerance` must state the general policy exactly: `ISO 2768-m`, or the `linear_mm` number. `standards.dimensioning` must belong to the regime.
- `requirements.yaml`: `REQ-###` statements with rationale, source, priority, method, and verification criteria.
- `interfaces.yaml`: mating, motion, clearance, electrical, or thermal contracts. `limits.press_fit` and `limits.running_fit` hold a `fit` designation and either a part `pair` or feature endpoints `hole` and `shaft` (`PN`, optional `occurrence: "@id"`, `feature`, optional `region`); `limits.heat_set` lists inserts as `{pair: [host, insert], hole_d, insert, source}` with optional `hole_tol`, `depth_min` and `note`. A pair item is a PN placed at most once or an `"@id"`; every PN must name a part record, and a fit on one occurrence never covers another occurrence of its PN. A `from`/`to` starting with `@` must name an occurrence.
  - A clearance requirement is a `type: clearance` interface. Its top-level `pair: [REF, REF]` names two parts, and its `min_clearance_mm` is above 0. A clearance interface without `pair` stays descriptive. Example:

    ```yaml
    - {id: IF-006, from: valve-3, to: piston-3, type: clearance, description: Valve 3 clears the piston crown., pair: ["@valve-3", "@piston-3"], min_clearance_mm: 1.0}
    ```

  - `validate.py` rejects a requirement with an unresolved reference or a value of 0 or less. It also rejects two references to one occurrence, and a second requirement on one occurrence pair.
  - cad-model `check` holds a requirement at the nominal pose, and cad-motion `sweep.py` at every sample. A joint or a fit on the pair does not exempt it.
- `assembly.yaml`: optional top-level `occurrences` (`id` lowercase, `PN`, optional `placement`: `translation_mm` and `rotation: {axis, angle_deg}`, rotation about the part's local origin first), subassemblies listing `parts` (each PN one implicit occurrence at the identity) and/or `occurrences: ["@id", ...]` (each explicit occurrence in exactly one subassembly; a PN with explicit occurrences is never also in `parts`), and joints with travel limits. `scripts/assembly_data.py` is the shared normalizer and reference resolver.
- `parts/<PN>/part.yaml` optional `model_frame`: `assembly_zero` (default; geometry in assembly coordinates at the zero joint pose, one identity-placed occurrence) or `part_local` (the part's own frame, placed by its occurrences).
- `parts/<PN>/part.yaml`: part number and revision, material, process, finish, mass target in grams, make/buy, optional supplier, and optional `decisions: [DR-###, ...]` references validated against `hw/decisions/`; `model.py` is the parametric CAD source.
  - Optional `procurement`: `mode` (`catalog` needs `make_buy: buy`; `made_to_drawing`), manufacturer and supplier part numbers, `designation`, `specification`, `open`, `approved_sources`, `qualification_evidence` and `certificates`. With open orderable identity, include its reason. `open` fields are not set elsewhere in the record. Keep a frozen `specification.artifact` copy in `parts/<PN>/sources/`.
  - Optional `manufacture`, for a custom-made part only (`make_buy: make`, or `procurement.mode: made_to_drawing`): `relationship: same` (made in its installed shape) or `different`. A different state, such as a strap printed flat, also needs `state`, `reason`, the approving `decision`, and `volume_rel_tolerance` or `volume_abs_tolerance_mm3`. Optional `mesh` overrides the STL tessellation (default 0.05 mm linear, 0.1 rad angular).
  - Optional `drawing`: `type` (`detail` for a made-to-drawing part; `vendor_specification` or `source_control` for a catalog item), `tolerance_policy`, `datum_features`, `coordinate_frame`, `views`, `features`, `dimensions` (requests without values, because every value comes from the model), structured `notes`, `manufacturing`, and `sheet`. `validate.py` checks that `datum_features` declares every datum label in use, that view and dimension ids are unique, and that each named tolerance policy exists in product.yaml and applies to the part's process.
- `bom.csv`: hierarchical EBOM; values and fields are checked against part records.
- `verification.csv`: requirement verification status and evidence; every requirement needs a row before release. An evidence cell may cite `hw/` paths, such as `hw/motion/v3/elbow-sweep`; `release.py` selects each cited bundle.
- `decisions/DR-###.md`: dated rationale and consequences for design decisions.
- `motion/cases/<case>/plan.yaml`: an authored cad-motion motion plan that the lead accepted; its schema is cad-motion `scripts/plan.py`. Case `default` is generated and never authored. `validate.py` loads each plan as `motion.py` does: it rejects a target on an unknown, fixed or coupled joint, a target outside the joint's limits, and an authored `default`. A member that `--attach` connects at run time does not stop the check.
- `releases/<rev>/`: an immutable release package that `release.py` writes, sealed by `manifest.json`. Version 1 manifests list project files in place; version 2 (`schema_version: 2`) seals byte copies, each with its sha256 and original. `validate.py` requires the directory and manifest revisions to match, inventory files to exist, verification results to be `pass` or `waived`, and no part to remain at an `X` prototype revision. A version 2 inventory names the package's own copies, whose originals may change or go after release.
- `.cad/recheck.json`: staged-index recheck stamp generated by `cad-recheck/scripts/stamp.py`; its JSON records the index tree hash, stage, checks, pass status, timestamp, and tool versions.
- `concept/<product-id>.scene.json`: L0 variants and rough primitives; validate it with `cad-concept` against the bundled scene schema.
- `concept/handoff.json`: chosen variant's flattened hierarchy, envelopes, joints, and alternatives; `validate.py` checks it against the adjacent `cad-concept` handoff schema when available, otherwise reports an informational skip.
- `concept/screenshots/<scene-sha256>/<capture-sha256>/`: concept viewer preview bundles.
- `docs/`: free-form notes, guides and reference material. It earns no geometry, check or release credit and never holds geometry or scripts.
- `assets/docs-templates/` contains the GitBuilding build guide, DIN SPEC 3105-1 checklist, and OKH manifest templates.

## Rules

MUST Validate the complete record before release; repair every reported finding before issuing a release manifest.
NOT Treat a nominal joint position outside its stated travel range as valid.
