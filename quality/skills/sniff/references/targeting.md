# Target Resolution

Sniff audits the whole repo or a **bounded slice**. Resolving a target is two
independent decisions, composed -- never a flat target→process matrix:

1. **Where does the code live?** → resolve the target to a *file set* + a
   *base ref* (if any), and decide **in-place vs. isolated checkout** materialization.
2. **How does each tool scope to it?** → each tool has an *analysis class*
   (see `tooling.md`) that decides whether file-scoping is honest, lossy, or
   wrong.

Do this in step 0.5 (after scope mode, before stack detect) so every later step
shares one file list and (when relevant) one checkout.

---

## 1. Target kinds → file set, base ref, materialization

| Target | User phrasing | Resolve file set | Base ref | Materialize |
|--------|---------------|------------------|----------|-------------|
| **Whole repo** | "sniff the codebase" | repo root (respect `.gitignore`) | -- | in place |
| **Language / area filter** | "just Rust", "the frontend", "only the Python" | filter the file set to that language's extensions (`.rs`, `.py`, …) or that area's globs (`frontend/**`, `apps/web/**`) -- resolve by language/area, NOT one path; the files may be scattered across dirs/crates | -- | in place (or layered, below) |
| **Module / dir** | "the auth module", "src/parser/" | glob the subtree | -- | in place |
| **File(s)** | "sniff foo.py" | explicit paths | -- | in place |
| **Working tree** | "my changes", "uncommitted" | `git diff --name-only` + `--staged` + untracked (`git ls-files --others --exclude-standard`) | `HEAD` | in place |
| **Commit** | "commit abc123", "last commit" | `git show --name-only --pretty=format: <sha>` | `<sha>^` | isolated checkout (recommended) |
| **Commit range / branch compare** | "since main", "last 3 commits" | `git diff --name-only <base>...<head>` | `<base>` | isolated checkout at head (recommended) |
| **Branch** | "sniff branch feature-x" | `git diff --name-only <base>...<branch>` | merge-base with default branch | isolated checkout |
| **PR** | "PR #42", a PR URL | `gh pr diff <n> --name-only` | PR base ref | isolated checkout |

**A language/area filter composes with any other kind** -- apply it as an
intersection on that kind's file set. "the Rust in this PR" = the PR file set
kept to `.rs`; "just the frontend, uncommitted" = the working-tree diff kept to
`frontend/**`. Resolve the base kind first, then filter.

Reduce every target to an explicit, deduplicated **file list** before step 1.
Drop deleted files (a diff lists them; nothing to sniff), then apply the
**file-set reduction** below. Echo the resolved list (or count + sample) so the
user confirms scope before tools run.

### File-set reduction (apply to EVERY target, including whole-repo)

This is not just for diffs. The biggest noise source is a **whole-repo** run over
committed vendored/generated trees (e.g. 205/231 `.py` under `archive/`, or
~1000 third-party files under `apm_modules/`). `.gitignore` does NOT help -- these
are committed. So always reduce, on every path:

1. **Drop vendored / build / tool / scaffolding directories** (committed but not
   first-party code): `archive/`, `vendor/`, `third_party/`, `node_modules/`,
   `dist/`, `build/`, `target/`, `.venv/`, `venv/`, `__pycache__/`, `.next/`,
   `.svelte-kit/`, `apm_modules/`, `apm_packages/`, `.specify/`, `.claude/`,
   `.codex/`, `.agents/`, generated SDK/proto output dirs -- and, for a *code*
   refactoring audit, design-doc scaffolding `specs/` and `docs/` (SpecKit
   spec/plan/tasks Markdown) unless the user explicitly targets docs. Prefer the
   language manifest to define the first-party set when available (Cargo
   `[workspace] members`, `pyproject` packages, `tsconfig` `include`).
2. **Drop generated files** -- detect, don't guess. Path/extension rules miss
   generated files with ordinary names (e.g. an `apm compile`d `.md`), so you
   MUST read headers:
   - **Header marker** -- `head -5` each surviving candidate and drop it if a line
     matches `Generated by` / `DO NOT EDIT` / `@generated` / `auto-generated` /
     `Code generated` / `apm compile`. One pass:
     `for f in <candidates>; do head -5 "$f" | grep -qiE 'generated by|do not edit|@generated|auto-generated|code generated|apm compile' && echo "DROP $f"; done`
   - **Known names**: `*.lock`, `*.lock.*` (`apm.lock.yaml`, `package-lock.json`,
     `Cargo.lock`, `poetry.lock`, `uv.lock`, `pnpm-lock.yaml`), `*.min.js`,
     `*.pb.go`/`*_pb2.py` and other codegen outputs.
   - **`.gitattributes`**: paths marked `linguist-generated`.
3. **Drop binaries / data blobs** (model files, images, `.onnx`, archives).

Echo first-party counts even on whole-repo runs ("231 .py → 26 first-party after
dropping archive/") so the user sees what was excluded. Findings in a generated
file recommend edits a regenerator will overwrite -- never include them.

### In-place vs. isolated checkout -- why it matters

- **In-place** (working tree, module, files): the code you want to read is
  already the current checkout. Operate directly, scope tools to the file list.
- **Isolated checkout** (commit, range, branch, PR): the ref's code may **not**
  match the current tree (you could be on a different branch). Reading the current
  tree would analyze the *wrong* file contents, and build-based tools (clippy,
  golangci-lint, `tsc`, `vue-tsc`) would resolve the wrong state. Materialize the
  ref via OMP task isolation (`isolated: true`) or a Worktrunk lease so tools see
  the code **as it is at that ref**, with that ref's own config files.

  Run tool probe, detection, and reading **inside** the isolated checkout. Handle
  these realities or the run silently analyzes the wrong thing:

  - **Resolve before you enter.** Compute the changed-file list and base ref from
    the MAIN checkout *first*; a detached isolated tree may not resolve every short
    SHA. Inside it, address refs by full SHA or the captured base ref.
  - **Don't rely on cwd persistence.** Agent harnesses may reset cwd between tool
    calls. Capture the isolated path as an **absolute literal** and pass it
    explicitly to every command (e.g. `semgrep ... <tmpdir>/<file>`); re-check the
    path exists before each tool run. (This is the same trap as the skill-relative
    asset path -- always absolutize.)
  - **A fresh isolated checkout has NO installed dependencies.** Build/import-aware
    tools (`pyright`, `mypy`, `tsc`, `vue-tsc`) will emit import-resolution errors
    that are environment artifacts, not smells. Either run `uv sync` / `npm ci`
    inside the checkout first, or treat type-checker import errors as a coverage
    gap and skip them -- never report `reportMissingImports`-class noise as findings.
  - If isolation is unavailable or the repo is shallow, fall back to in-place
    diff-scoping and note the reduced fidelity.

  Offer the isolated path; if the user prefers a quick in-place diff (and is on
  the right branch), honor that -- it is faster and usually fine for same-branch
  commit ranges.

## 2. Tool scoping by analysis class

A target file list does NOT mean "pass those files to every tool." What a finding
*depends on* decides correct behavior. Each tool is tagged with an **analysis
class** in `tooling.md`; scope by class:

| Class | Examples | Scoping rule in a bounded run |
|-------|----------|-------------------------------|
| **Local** -- finding lives inside one file/function | ruff `C901`, clippy, shellcheck, magic-number, naming, idioms | ✅ Pass the file list directly. Honest and faster. |
| **Relational** -- finding is a *link* between target and other code | jscpd (duplication), feature-envy / coupling | ⚠️ Scan target **+ repo context**; report only links that touch a target file. (Diff-only would miss that new code duplicates *existing* code.) |
| **Global** -- project-wide invariant | knip / vulture / `deadcode` (dead code), madge (cycles), cargo-machete (unused deps) | ❌ **Do NOT naively scope** -- an export unused *within the diff* may be used elsewhere, so file-scoped dead-code yields "delete this" on live code. **Skip in scoped mode + note it** (see below). |
| **Baseline** -- the analysis *is* a comparison vs. a ref | buf breaking, graphql-inspector diff, openapi diff | ✨ A diff/PR/range target is the tool's **native mode**. Run against the base ref. Headline the result (see below). |

### Concrete per-tool scoping

- ruff: `ruff check --output-format json <files>` (see `languages/python.md` for rule-selection flags -- never bare `--select`, it discards project config)
- eslint: `npx eslint --format json <files>`
- shellcheck: `shellcheck -f json <files>`
- semgrep: `semgrep --config <ruleset> --json <files-or-dirs>`
- golangci-lint: scopes per-**package**, not per-file. Run
  `golangci-lint run --out-format json <dirs-of-target-.go-files>`, then
  **filter** the JSON to paths in the target set.
- jscpd (relational): run over target + its directory, report blocks touching a
  target file.
- Config/whole-file linters that take no path list: run normal scope, then
  **filter findings** to the target file set.

## Global analyses in scoped mode -- skip + note

In a scoped run (anything but whole-repo), **skip global-class analyses by
default** and record it explicitly in the report:

> Coverage note: dead-code, circular-dependency, and unused-dependency checks
> were **skipped** -- they need whole-project context, and scoping them to a diff
> reports false positives (code unused *here* may be used elsewhere). Run a full
> `sniff` to include them.

Offer to broaden ("run dead-code on the whole project, then filter to your
files") on request. **Never** silently file-scope a global tool -- that is how a
sniff ends up recommending deletion of live code.

## Breaking-change detection -- headline it for ref targets

When the target is a **diff / PR / commit-range / branch** AND it touches an API
contract (`.proto`, `.graphql`/`.gql`, OpenAPI specs), run the baseline tools
against the base ref:

- Protobuf: `buf breaking --against ".git#ref=<base-ref>,subdir=<proto-dir>"`
- GraphQL: `graphql-inspector diff <base-schema> <head-schema>`
- OpenAPI: an openapi diff (`oasdiff`/`openapi-diff`) base vs. head

**Code-level public APIs (no IDL file).** The tools above only cover wire/IDL
contracts, but the headline break is often in code: a changed/removed exported
function signature, a new required parameter, a `typing.Protocol` change, or a
pydantic field added/removed/renamed on an `extra="forbid"` model. There is no
linter for this -- diff the **exported** surface against the base ref yourself
(`git diff <base>...<head> -- <public modules>` focused on `def`/`class`/exported
signatures and model fields) and headline any backwards-incompatible change the
same way. This is frequently the most valuable finding on a feature PR.

Surface any contract break (wire OR code-level) as a **top-severity, dedicated
report section** ("⚠️ Breaking API changes vs. `<base>`"). For a PR this is often
the single most valuable finding -- and it only exists because there is a base
ref. A whole-repo sniff cannot produce it.

## Report framing shifts with the target

Same engine, different headline (reflect in `report-template.md`):

- **diff / PR / range** → *regression review*: "what did this change make worse,
  and what did it break?" Lead with breaking changes, then new smells the change
  introduced, then adjacent issues.
- **module / dir** → *mini-audit* of that component.
- **file(s)** → *focused read*.

## Out-of-target findings

A tool may surface a real issue just outside the target (e.g. the function a
changed line calls). Keep these in a separate **"Adjacent (out of scope)"**
subsection -- don't drop them silently, don't mix them into the prioritized plan.
The user chose the scope; respect it, but don't hide a landmine next to it.

## Diff-aware nuance (changed files vs. changed lines)

Default to **whole changed files**, not just changed hunks: a smell often sits a
few lines from the edit, and file-level is what tools report. Narrow to changed
lines only on explicit request ("only the lines I touched") -- then intersect
findings with the diff's hunk ranges (`git diff -U0`), and note the narrowing.

## Apply-mode and scope boundaries

In a scoped run, a fix (e.g. Extract Method) may move code *out of* a target
file. Apply must respect the boundary: if a low-risk fix would touch files
outside the scope, surface that ("this fix also edits `utils.py`, outside your
scope -- proceed?") rather than silently editing beyond what the user asked for.

## Dependencies

- `git` -- required for working-tree / commit / range / branch / isolated targets.
- `gh` -- required for PR targets (`gh pr diff`, `gh pr view`).
- If a repo is not a git repo, only whole-repo / module / file targets apply.
  If `gh` is absent, ask for the PR's branch/base and fall back to range mode.

## Examples

- *"sniff PR #128"* → isolate the PR head → `gh pr diff 128 --name-only` = 6
  files (4 TS, 2 `.proto`) → detect TS + Protobuf → eslint on the 4 TS files;
  `buf breaking --against ".git#ref=<base>,subdir=<proto-dir>"` on the protos → **breaking-change section
  headlined**, then TS smells → global dead-code skipped + noted → plan covers
  only those 6 files.
- *"sniff the parser module"* → in place, `src/parser/**` → Rust → clippy on the
  crate, filter to `src/parser/` paths → one bloodhound → scoped mini-audit.
- *"sniff since main"* → isolate at `HEAD` → `git diff --name-only main...HEAD`
  → per-language local tools scoped; breaking-change vs. `main` if contracts
  changed; global analyses skipped + noted.
